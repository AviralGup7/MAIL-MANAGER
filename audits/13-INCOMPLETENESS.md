# 13 · Severe incompleteness audit

**Subject:** BITS Mail Manager at `d11773e`.
**Question:** what is half-built, one-way, or unreachable?
**Method:** probed the running code — verb tables against call sites, settings
against readers, `actionsFor()` against the controls that consume it.

Not a polish audit. Everything below is a capability that **exists in the code
and cannot be used**, or a workflow the user can start and not finish.

---

## The headline

**A message in Trash has zero available actions.** Not "limited" — zero. Every
flag in `actionsFor('trash')` is false except `restore`, and nothing consumes
`restore`. You can open a deleted message and do nothing with it.

That is the shape of most findings here: the model is right, the plumbing is
right, and the last wire to the UI was never run.

---

## The completeness matrix

Generated by calling `actionsFor()` for each mailbox and intersecting with the
controls that actually exist:

| Mailbox | Usable actions | Declared, no control |
|---|---|---|
| inbox | star, archive, trash, snooze, spam | — |
| starred | star, archive, trash, snooze, spam | — |
| snoozed | star, archive, trash, spam, **unsnooze** ✅ | — |
| sent | star, trash | — |

| spam | trash, spam | notSpam ✅ *(handled by the flipping label)* |

## 🔴 Core — the product is not complete without these

### I-1 · Trash is a dead end — ✅ **FIXED**

**What's incomplete.** No restore. `UNTRASH` exists in the worker and is called
from exactly one place: the undo stack. If you delete something and undo
immediately, fine. If you notice tomorrow, the message is unreachable forever
from inside this product.

**Why it matters.** "I deleted the wrong thing" is one of the most common
things a person does with mail. Gmail's Trash is a *recovery surface*; here it
is a viewing gallery.

**What's missing.** A control bound to `restore`, calling the existing verb.

**Core.**

### I-2 · Drafts cannot be opened

**What's incomplete.** `actionsFor('drafts')` returns `edit: true`. Nothing
reads it. You can see your drafts and delete them. You cannot continue writing
one.

**Why it matters.** A draft exists *only* to be finished. The product already
has compose, autosave and crash recovery — this is the one path that would
connect them to the Drafts mailbox, and it was never wired.

**What's missing.** An Edit control that loads the draft into compose. Needs a
worker verb to fetch the draft body (`SAVE_DRAFT` exists; there is no
`GET_DRAFT`).

**Core.**

### I-3 · The classifier can be taught but never corrected — ✅ **FIXED**

**What's incomplete.** `correctSender()` and `clearCorrection()` are both
implemented, tested, and **called from nowhere**. `applyCorrection()` — the
read side — runs on every ingest. So the system faithfully applies a
correction store that no user can write to.

**Why it matters.** This is the product's headline differentiator. Fifteen BITS
categories and ~1000 rules, and when it puts something in the wrong bucket the
user's only option is to live with it. The README describes correcting the
classifier as a feature.

**What's missing.** A "wrong category?" affordance in the reader, and a way to
list and clear existing corrections.

**Core** — it is claimed in the docs and absent in the product.

### I-4 · Snoozed mail cannot be woken — ✅ **FIXED**

**What's incomplete.** `unsnooze` is declared, `UNSNOOZE` exists in the worker,
`removeSnooze()` exists in the domain, and `wakeLabel()` is *imported into
app.js and never called*. A snoozed message also never displays **when it
wakes**.

**Why it matters.** Snooze is a promise about the future. A list of messages
that will return at unstated times, with no way to change your mind, is worse
than not snoozing them.

**What's missing.** The wake time on the row, and a control to wake now.

**Core.**

---

## ⚠️ Important

### I-5 · A message's own deadline is invisible in the reader

`dueAt`, `dueKind` and `dueText` are extracted, stored, cached, re-derived on
warm start — and surfaced **only** in the sidebar radar, which shows at most
six and only the urgent ones. Open the message itself and the deadline the
product worked out is nowhere.

The reader is exactly where "this is due Tuesday" belongs.

### I-6 · Labels are read-only

`label:` searches. The palette lists them. `CREATE_LABEL` exists and is called
only internally by `ensureLabel` for snooze. You cannot apply, create or remove
a label on a message.

Already recorded in audit 12; repeated here because it is the same shape —
read support without write support.

## Optional

- **`confidence` and `reason`** are stored per message and shown only when the
  classifier is unsure. That is a deliberate design decision, not an omission.
- **Attachment preview** — download works; no inline viewer.
- **`GET_DRAFT`** does not exist as a verb, which is what blocks I-2.

## What I checked and found complete

Stated because an audit that only reports gaps is not evidence of having
looked:

- **Every background verb is reachable** except `CREATE_LABEL` (internal to
  `ensureLabel`) and `WAKE_DUE` (alarm-driven). Both correct.
- **Every setting is read** where it should be. `clientId` is read by the
  worker rather than the app, which is right.
- **Spam is genuinely two-way** — the flipping label handles `notSpam`, so that
  declared flag is not orphaned.
- **Threading, auto-refresh, attachments, Bcc** — all wired end to end,
  verified in the previous three sessions.

## The answer

**What is still missing before this is complete?**

Originally four mailboxes were partially inert. **Three are now wired**:
Trash restores, snoozed mail wakes, and the classifier can be corrected and
un-corrected.

What remains: **you cannot open a draft to finish it**, and labels stay
read-only. The draft one is the real gap — a draft exists only to be finished,
and the product has compose, autosave and crash recovery already; this is the
single path that would connect them to the Drafts mailbox.
